# AI 重复点击已点击过的区域，导致提前终止（2026-10-17 修复）

> 起因：`context-log/2026-08-25_待修问题清单.md` 第 4 条（当初按"日志已不在磁盘"处理、未定性；实际是混淆了时间相近的日志）。本次用两处真实日志定性根因、改掉计数口径，并补了可复用的假 Agent 回归。

## 现象

两处真实日志、同一机制：

**`xor_agent_20260825_215157.log`（旧项目 `Repositories2\test-agent-2`，21:51:57–21:55:08，未开详细日志）**

```
失败：点击达到 64 次。已点击 50/63 个非种子区域。
统计：循环 4 次，工具调用 66 次，成功点击 64 次。
```

4 轮 64 次 `set_region`，只有 50 个不同格子：1~14 号格各被点 2 次。第 1 轮先设一批（值 1,3,7,13,…,63,-10,-27,-43），第 2 轮**按新设计整批覆盖 1~14 号格**（值 11,19,27,27,…,23）后再继续点 15~21。13 个格子从未被点。

**`xor_agent_20260825_211223.log`（21:12:23–21:16:00，开详细日志）**

```
失败：点击达到 64 次。已点击 61/63 个非种子区域。
统计：循环 10 次，工具调用 72 次，成功点击 64 次。
```

64 次 `set_region` 全部成功，只有 61 个不同格子：2、3、4 号格各 2 次。62、63 号格从未被点。

## 根本原因

**"允许调整"与"总点击上限"两个设计互相冲突。**

- 系统提示词要求"设定后用 view_region 核对……不一致就调整"，但当时 `set_region` 没有任何重复上限，每次成功都写进点击轨迹并计入 `click_count`；全局上限 64 次（`MAX_CLICKS` / `--clicks`）。
- 成功判定用去重的 `coverage()`，重复点击不加覆盖、只吃预算。于是**重复 k 次就少覆盖 k 格**：重复 1 次刚好卡在 64 次时覆盖 63（成功），重复 ≥2 次必然提前终止。
- 日志实测（`211223`）：64 次 `set_region` 全部成功，只有 61 个不同格子；重复的是 2、3、4 号格各 2 次。

**模型为什么重复（用户原怀疑"那轮 AI 改了设计"，成立）**：`211223` 里第 2 轮先用 1~4 号格做负值语义验证（`idx2=-2, idx3=4, idx4=-5`），第 3 轮确认反色规律后按正式设计回改，思考原文：

> So I need to fix idx2 (2 instead of -2), idx3 (3 instead of 4)

`215157` 是同一个行为的更大规模版本（整批 14 格重设），只是没开详细日志、看不到思考。即"先试点几格/先设一批，再按定稿设计整批覆盖"是提示词鼓励的正常行为，不是误操作。

## 测试方式

两种手段，用途不同，别混：

1. **机制复现（假 Agent，不花 token）**——把 `agent.chat_stream` 换成按脚本逐轮返回工具调用的假函数，直接跑真实 `agent.main()`（工具执行、快照、终止判定、结果判定全走真链路）。临时探针实测：
   - 同一格不重复 → 63 次点击、覆盖 63、成功；
   - 同一格多点 1 次 → 64 次点击、覆盖 63、成功（正好卡上限，无余量）；
   - 同一格多点 2 次 → 64 次点击、**覆盖 62、区域 63 从没被点、失败**。
2. **日志取证**——按 `set_region id=… args={…} -> …` 行统计每格出现次数（本轮修复就是靠它定性的）。注意旧日志的 args 是 Python repr，**单引号**，正则别只认双引号。
3. `tests/sim_agent.py` **不能**用于这类验证：它按日志回放，绕过主循环的计数器与终止判定，只能测 UI。

## 修复方式

按用户拍定的口径（每格 3 次含首次、工具调用 240、超上限拒绝但不计无效）：

| 文件 | 改动 |
|---|---|
| `xor_world.py` | 新增 `MAX_SET_PER_REGION = 3` 与 `set_count(index)`；`set_region` 第 4 次起拒绝，返回 `区域 N 已设定 3 次（上限 3 次），本次未修改；当前值 …`（**不带 `Invalid` 前缀**）；成功返回值加 `（第 n/3 次设定）` |
| `tools.py` | `set_region` 描述写明"可调整已设定过的区域；非种子区域最多设定 3 次（含首次）" |
| `agent.py` | `MAX_TOOL_CALLS` 96 → 240；删掉 `MAX_CLICKS`、`--clicks` 与"点击达到 N 次"终止分支；成功点击数改由 `xor_world.state["clicks"]` 派生，统计行加"其中重复调整 k 次"；系统提示词写明单格 3 次上限、结束条件改为"工具调用次数将尽" |
| `web/index.html` | 状态栏改为 `点击 N 次 · 已覆盖 k/63 格`（允许调整后点击数会超过 63，只显示点击数会让人误解） |
| `tests/fake_agent.py` | **新增常驻**：6 条用例（正常路径、每格 2 次仍成功、单格第 4 次被拒、连撞上限不误终止、连撞种子仍按连续无效终止、工具调用 240 次终止且点击 189 次） |
| `tests/selftest.py` | 加单格上限断言（含"超上限不得带 Invalid 前缀"） |
| `README.md` / `TECH_DESIGN.md` | 用法与终止条件同步（去掉 `--clicks`，写明单格上限与 240 次） |

**关键点：超上限的返回不能带 `Invalid` 前缀。** 主循环把 `Invalid` 计入连续无效点击（3 次即终止），超上限是"用尽"不是"参数错误"，否则模型连撞 3 次上限就会被误判成乱传参数而提前终止。

**为什么不用"总点击上限改按去重计数"这个更小的改法**：它也能让重复点击不吃预算，但会把 `--clicks` 变成一个永远不该触发的开关（默认 64 ≥ 63），语义含糊；用户选的是"去掉总点击上限 + 单格 3 次"，边界更清楚：单格上限管浪费，工具调用上限管跑飞。

## 真实运行验证（2026-10-17 21:11，改后首跑）

`xor_agent_20261017_211106.log`（种子区域 0 = -3，21:11:06–21:16:12）：

```
成功：模型直接输出文字，未再调用工具。已点击 63/63 个非种子区域。
统计：循环 11 次，工具调用 86 次，成功点击 65 次（其中重复调整 2 次）。
```

- 工具构成：`set_region` 65、`view_region` 19、`evaluate` 2；`state.json` 里 `status=success`、11 轮、65 条 clicks。
- 重复的正是 1、2 号格各 1 次：第 2 轮先拿这两格试语义（设成 `-4`、`3`），第 3 轮按定稿设计回改——与两处旧日志同源，但这次没有代价。
- **旧规则下这次会失败**：点击总数 65 已超过 64，第 64 次点击时覆盖 62 格，会停在"点击达到 64 次。已点击 62/63"，末轮总结根本不会发生。
- 提示词生效证据（模型自己的思考）：`each at most 3 clicks`、`I have 2 sets each remaining`、`using the remaining refinement opportunities (each region has 2 sets left, except 1 and 2 which have 1 left)`——它把单格额度当成了规划资源。
- 全程 0 次超限拒绝、0 次 `Invalid`（grep 日志无"上限/Invalid"），说明 3 次上限没被误触，也没带来新的摩擦。

## 经验

- **"允许调整"的机制必须配"重复额度"**：提示词鼓励回改之后，第一次实测就出现重复点击，看起来模型会先试点几格验证规律，再回改。计数器若按"动作次数"设总上限，重复就是纯浪费；上限应该按"去重目标"或"单目标次数"设。
- **假 Agent（假流式 client + 真实 `main()`）是验证终止条件与计数口径的正确层次**：`selftest` 只测函数、回放器绕过主循环，只有它能证明"这串操作会不会提前终止"，且零 token。
- **给模型设硬边界要在三处同时说**：工具描述、系统提示词、工具返回值（`第 n/3 次设定`）。只改代码不改提示，模型只能靠撞墙发现边界。
- **拒绝语义要分层**：参数错误（`Invalid`，会计入终止）vs 用尽（普通拒绝，不计入终止）。混在一起就会被自己的终止条件反咬。
- **时间戳相近的日志先核对内容再定性**：同一晚可能有"缺密钥的 1KB 空跑""未开详细日志的纯结果日志""完整详细日志"三种。判别特征：文件大小、首行 `DETAILED_LOG … → detailed=…`、结尾 `成功/失败` 统计行。当初把 `215015`（空跑）当成唯一线索，就得出"日志不在磁盘"的错误结论。
- **改完要拿一次真实运行收尾**：假 Agent 只能证明"重复会怎样"，不能证明"模型在新约束下怎么规划"。这次真实运行的思考里出现了 `each at most 3 clicks`、`2 sets each remaining`，说明写进提示词的额度被模型当成资源在用；同时确认没有超限拒绝带来的摩擦。
