## 方案 A 前端关键逻辑（存档，正式 index.html 同款）
`drawTimeline(clicks)`：按 round 分组；进行中轮（`liveRound>0 && g.round===liveRound`）思考用 `liveText.slice(0, liveShown)`（打字机截断版）并标「思考中…」（放完 `liveShown>=liveText.length` 时标记消失）；历史轮显示 `g.reasoning` 完整思考；**无任何点击的新轮**（刚开新一轮或 evaluate/view 轮）单独追加一组「第 N 轮 · 0 格 · 思考中…」。
`tick()`：先 `await refreshLive()`（更新 liveText/liveShown/liveRound）再 `await refresh()`（渲染，timeline 依赖 liveText）——顺序不能反。

## 修正：移除 60 字符/秒打字机节流（同日，用户实测）
用户跑真实 `agent.py` 后反馈：**终端显示速度快于 UI**。根因：前端曾为"防一次显示完"设 `LIVE_TICK=60` 字符/秒固定节流，但真实 API 思考 delta 到达更快（agent 每收一个 delta 就 `print` + `write_reasoning_live` 一次），60/秒成了人为瓶颈，UI 落后于终端——正是 AGENTS.md 错误假设示例「实际 API 速度是 60 字符/秒」。

修复（web/index.html）：去掉 `LIVE_TICK` 与 `liveShown` 截断，`refreshLive` 直接取 `reasoning_live.json` 当前全文（`liveRound`/`liveText`），显示速度 = 文件更新速度 = 真实 delta 速度 = 终端速度；轮次切换直接替换文本。`drawTimeline` 相应简化（去掉 done 判断，live 轮恒标「思考中…」直到文件被下轮覆盖/删除）。node+vm 12 项断言全过。未动 agent.py 兜底写：真实流式下 reasoning 是增量 delta，兜底一次性返回场景先观察，若再现"一次全出"再加 agent 端拆块慢写。

## 待修 bug 记录（2026-08-24 真实运行，用户实测）
1. **UI 最后几个格子没标上，终端有**：真实运行完成时，页面「AI 决策过程」卡最后几个 set_region 未显示，但终端已输出。疑点：最后一轮点击后运行立即结束（coverage==63 判定），UI 最后一次 1 秒轮询未抓到最终 state.json，或最后几格点击与结束快照时序竞态。

3. **思考输出中途变慢**（用户观察："输出一些内容之后很慢，每秒新增词语数量很少，中断再测仍慢，暂停等一会再测就快"）：终端与 UI 同步慢 → 瓶颈在数据源（API 生成速度），非前端。215251 日志轮 1 思考 172.9s 佐证 deepseek 长思考本身慢；但 `write_reasoning_live` 每 delta 写累积全文（O(n²)，文本长+delta 碎时开销大）可能加重 agent 侧负担，待查。
