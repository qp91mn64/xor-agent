## 现象与判断

| 现象 | 判断 | 处置 |
|---|---|---|
| a. 首次响应约 47 秒无反馈，误以为卡死 | 真问题：阻塞式等待期零反馈 | 修：流式 + 实时思考（控制台 + web） |
| b. 作弊解不唯一：1/2/4/8/16/32 任一单一位值即满分，作品视觉单调 | 已知限制（TECH_DESIGN 已记"已知坑"），实测证实且范围比文档描述更广 | 记录；v1 指标不动，审美留后续扩展点 |
| c. 模型一次请求批量返回 16~31 个工具调用，4 轮画完 63 格 | 模型正常能力（function calling 支持并行返回），非 bug；不限制（强制逐格会增至 60+ 轮，慢且贵） | 记录 |
| d. 可视化一次刷新一堆；思考（一轮一次）被记进该轮每个点击，时间线大量重复 | 半问题：批次刷新是落盘节奏的必然，可接受；思考重复是呈现缺陷 | 修：clicks 加 round，web 按轮分组 |

## 决策

1. **a**：agent.py 改流式（`stream=True`）。思考增量实时打印控制台 + 原子写 `output/reasoning_live.json` 供 web 轮询显示；每轮打印请求耗时；运行结束删除中间文件。
2. **d**：`set_region` 记录 `round`（轮次，一次 API 请求 = 一轮）；web 时间线按 round 分组——一组显示一次思考 + 该批格子，最新 15 组。
3. **b/c**：TECH_DESIGN 的"已知坑"补实测结果；主循环描述补"模型可一次返回多个工具调用（批量并行）"。

## 成本结论（回答"流式是否影响 token 消耗"）

- **流式不影响计费**：流式与非流式消耗 token 数量相同，只是传输方式不同（来源：DeepSeek API 文档镜像 FAQ、deepseekai.guide "Streaming is purely a transport choice"）。
- 真实成本大头：
  - reasoning_content（思考）token 计入输出计费，且思考往往很长（首次思考约 120 行）；
  - agent 场景每轮回传完整历史（输入侧累积），DeepSeek 默认磁盘缓存命中后输入价格降约 98%。
- V4 Flash 价格（2026-04 快照）：输入 $0.14/1M（cache miss）、$0.0028/1M（hit）、输出 $0.28/1M。
